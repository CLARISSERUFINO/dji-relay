## Phone side

- Live sender: its own queue (a stream consumer like the phone recording), socket bound
  to the Wi-Fi network with `Network.bindSocket`, traffic class `0x88` (DSCP AF41),
  low-latency Wi-Fi lock held while streaming (`WIFI_MODE_FULL_LOW_LATENCY`).
- RTP timestamp = `pts_ms` × 90; header extension with `t_rx_ns`, `pts_ms`, `frame_idx`,
  `segment` on the first packet of each access unit (`docs/protocol.md`).
- "Live streaming" toggle, off when the app starts; PC IP entered in the app and saved.

## `drone_logger` (PC)

- `libcommon::UdpUnicastReceiver`: unicast, `recvmmsg`, kernel receive time
  (`SO_TIMESTAMPNS`), 8 MB receive buffer.
- Frame assembly by RTP timestamp up to the marker bit; one row per access unit in
  `live_frames.csv`. Injection time per frame in `injected_frames.csv`.
- Two GStreamer pipelines:
  - **stream pipeline**, one per stream (new SSRC, or after no packets for
    `DRONE_STREAM_TIMEOUT_MS`): `appsrc` → `rtpjitterbuffer` → `rtph264depay` →
    `h264parse` → `video_live_NN.mkv` + decoder → YUY2 → `appsink`;
  - **injection pipeline**, kept for the whole run so `/dev/video10` stays open across
    stream interruptions: `appsrc` → `v4l2sink` (+ display window).
- Health line once per second: packets/s, Mb/s, frames/s, decoded/s, injected/s, lost
  packets, incomplete frames, injections dropped, SSRC, segment.

## Issues found

1. **Stream callbacks do not resume after a drone reconnection.** After the drone was
   power-cycled, the app re-added the `ReceiveStreamListener`, the pilot view showed
   video, but the listener received no callbacks. Fixed with a watchdog in
   `StreamReceiver`: while attached and without callbacks for 5 s, the listener is
   removed and added again (at most every 5 s). In the test it took two re-adds; the PC
   video came back about 10 s after the drone reconnected. The watchdog does not fire
   on a normal start (first callback after about 3 s).
2. **v4l2loopback `max_buffers=2` is too small for SSL-Vision.** SSL-Vision's V4L module
   requests 3 buffers (`V4L_STREAMBUFS` in `capturev4l.h`) and fails with
   `REQBUFS returned error, count 2`. Fixed by loading v4l2loopback with
   `max_buffers=4` (`docs/dev-environment.md`, section 5.3).
3. **v4l2sink caps.** v4l2loopback 0.12 only accepts YUY2 caps that state
   `interlace-mode=progressive` and `colorimetry=2:4:7:1`, and v4l2sink refuses the
   decoder's extra fields (`not-negotiated`). The injection pipeline sets plain caps with
   those fields (labels only, no pixel conversion).
4. **No frame rate in the drone's SPS.** The decoded caps say `framerate=0/1`, which
   v4l2sink refuses. The injection caps are labelled 30/1, the rate `StreamInfo`
   reports; frames are still passed on as they arrive (`sync=false`).
5. **First frames without an RTP timestamp in `injected_frames.csv`.** About the first
   0.5 s of each stream (14 frames in the bench test) cannot be matched to an RTP
   timestamp while the jitter buffer settles; later frames all can. Relevant for E10 (F4).
6. **Bench overheating.** With the motors off there is no airflow over the drone, and
   it overheated during the tests. Power it off between tests, and use a fan for long runs.
